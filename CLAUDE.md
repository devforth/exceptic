# CLAUDE.md

## Project

Self-hosted error and log monitoring server that accepts data from the official Sentry SDKs via DSN (envelope protocol). Go, an embedded key-value store (goleveldb, pure Go, no CGO), shipped mainly as a Docker image (`FROM scratch`, size budget 50 MB, currently ~20 MB, ~6 MB to pull). MIT, public DevForth OSS project. Tracklify task: `DevFo-OSS/17`.

Scope: errors and logs only. Tracing spans, session replay and uptime items are accepted and dropped, not stored; `client_report` items are only counted (dropped data per project).

Done: stages 0 protocol research, 1 skeleton, 2 ingest, 3 data model and grouping, 4 REST API, 5 UI and 6 notifications (Slack and Telegram short, email full), 7 retention (cleanup by size), 8 packaging and docs, 9 MCP, plus users with roles, the issue status history and per-project disk shares. The web UI is a SvelteKit SPA (`web/`). Next: the first release (tag `v0.1.0`), Google sign-in.

## Commands

Go is installed in `~/.local/go`; if `go` is not on PATH, run `export PATH="$HOME/.local/go/bin:$HOME/go/bin:$PATH"` first.

```sh
make test         # go test -race ./...
make lint         # golangci-lint (.golangci.yml): vet, staticcheck, errcheck, gofmt/goimports, wsl blank lines
make fix          # auto-fix formatting, import order and blank lines; run after editing Go code
make build        # static binary to bin/exceptic
make docker       # build image devforth/exceptic:dev
make image-size   # fails if the image is over MAX_IMAGE_MB (50)
make web          # build the SPA (web/, Node 24 + pnpm) into web/dist/spa, which Go embeds; make build runs it
make web-check    # svelte-check, prettier --check, eslint, vitest
make api-types    # rewrite web/src/lib/api/catalog.gen.ts from the catalog; make test fails while it is stale
make dev          # the user runs it (tools/dev.sh): everything at :8000 in one terminal, the app with hot reload (Vite) and the Go server behind it on :8001 (Ctrl+C stops both)

go test ./internal/storage/database -run TestUserRules -count=1   # single test
go test ./web                                                     # checks a built SPA page against what Go expects (skipped when not built)
```

Do not start the server (`make run`, `docker run`, …) yourself; the user runs it in their own terminal. Check it with `curl localhost:8000/health` and ask the user to start it if it is not reachable. `make run` loads `.env` and `.env.local` (gitignored; template in `.env.example`); without projects (`PROJECTS` or added in the web app) every event is rejected: the start logs a warning, each rejected envelope only a debug line (`LOG_LEVEL=debug`). `.env.example` holds placeholders only; the real keys and passwords go into `.env.local`. `go run` does not rebuild on change: after editing Go code (or rebuilding the web app, which is embedded), the user must restart it.

The image has a writable `/tmp` (scratch has none). CI (`.github/workflows/ci.yml`) runs golangci-lint (pinned version), `make test`, `make web-check web` with `go test ./web`, an amd64 image build with the size check and an arm64 build. `release.yml` runs on a `vX.Y.Z` tag: it calls `ci.yml` (`workflow_call`), then pushes `devforth/exceptic:X.Y.Z`, `:X.Y` and `:latest` (not for pre-releases) for amd64 and arm64 to Docker Hub (secrets `DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN`). `compose.yml` is the example deployment the docs refer to.

## Architecture

Where to look first:

| What | Where |
|---|---|
| Startup, shutdown, subcommands | `cmd/exceptic/main.go`; the server built and run by `internal/app` (`app.New`, `app.Run`) |
| Every periodic job and its lane | `internal/app/jobs.go` (the database lane: `database.Store.Lane`); the runner `internal/platform/background` |
| Schedules, time limits, size limits | `internal/platform/config/schedule.go`, `retention.go`, `ingest.go` (what one log or event may store) |
| All settings from env | `internal/platform/config` (documented in `docs/configuration.md`) |
| HTTP mounts (health, ingest, API, the web app's API, MCP, OAuth, web app) | `internal/server/server.go`; the web app at every other address (`web/web.go`) |
| REST endpoints, MCP tools, the web app's requests | `internal/api` (one catalog entry each; `rest.go`, `mcp.go`, `ui.go`) |
| Rules of the application | `internal/services` (the only way the web app and tools reach data) |
| Storage records and their rules | `internal/storage/store`; every collection and index in `internal/storage/database/schema.go` |
| Ingest path | `internal/ingest` (handler → inbox → pipeline → `StoreSink`) |
| Notifications | `internal/notify` |
| The web app | `web/` (SvelteKit project and Go package `web`) |

`internal/`, grouped by area:

- `platform/`: what every part uses: `background` (the lanes of periodic jobs), `config` (with the field limits and the level order, `HighestFirst`/`InLevelOrder`, and `ShownLevel`, the color group of a level in the web app and emails), `logging` (also `PanicError`: a recovered panic as an error with its stack, used by every recover: lanes, HTTP, ingest, notify, MCP tools), `secret`, `textutil` (`TruncateRunes`, `Shorten` with "…", `TruncateBytes`, `ShortenBytes` (at most n bytes where a character starts, then "…" after them), `ContainsFold` (substring ignoring the case of ASCII letters, the log and issue search), `EmailLocalPart`, `Slug` (`AppSlug`, prompt file names), `IndentJSON`, `MaskSecret`, `AuthCredential` (Bearer/Basic in text, for `agentprompt`; `scrub` has its own wider one), `ReplaceServiceTokens` (chat services' tokens in URL paths, for both)).
- `app/`: the server built from its parts (`New`, for main and the tests), run with its background work (`Run`), the periodic jobs (`jobs.go`) and the backup socket's handler.
- `server/`: the HTTP shell: the routes of the whole server and `/health` (`server.go`), the IP allowlist and token (`access.go`), security headers, the CSP builder and the Origin check (`headers.go`), JSON answers (`json.go`), the control socket of backups (`control.go`).
- `ingest/`: receiving from Sentry SDKs (handler, pipeline, `StoreSink`, `compact.go`, `scrub.go`) with `grouping`.
- `sentry/`: the SDK wire format, read by ingest, notify, services (the issue page) and the agent prompt.
- `storage/`: `store` (the API of the storage: the records, their rules and the `Store` interface, every operation on the records; everything else uses only it, except the inbox (`ingest.Pipeline`) and the periodic jobs and backups (`internal/app`, the database lane built by `database.Store.Lane`), which take `*database.Store`), `database` (the one implementation of that API: every record, the ingest inbox included, each collection declared in `database/schema.go`; the engine is picked in `database/engine_leveldb.go`, the only file naming it), `kv` (the layer under it, unaware of the application: keys built from typed parts, collections with declared indexes, batches with counters and sequence numbers, queries and cursors (`Head` decodes only a record's head when the collection has `DecodeHead`, as events, the inbox and the outbox do; `Raw` filters on the stored bytes before decoding; `Keyed` on the record's key before reading it, through an index too; `Count` without `Where`, `Raw` or `Keyed` counts keys; `WithContext` ends a walk with its context; `Cursor.Step` reads one key, a skipped one too, so merged walks advance together), `Check` (`Schema.Check` runs it on every collection, as `Store.Verify` does), the `Engine` interface (`SizeOf`: the files' bytes of a key range, deleted keys included until compacted); `Definition.Tally`: record counts per key (how many records have a status in a project, say), written in the same batch under `tally/`, apart from the byte counters (`DB.Tally`, `DB.Tallies`, `DB.CheckTallies`; beside a Backfill only of indexes, not of the Group); `Write` neither deletes nor puts again the index keys a rewrite keeps, and they leave nothing stale; `Definition.Group`: a second byte counter per record (the project), written in the same batch under `group/` and kept apart from `Counter`'s (not in `Batch.Counted`, `DB.Written` or the cleanup's total; `DB.Groups`); `Collection.Stale`: per counted collection, the bytes its deletes and rewrites left in the files, counted in the same batch under `stale/` (all ever added under `staled/`: `StaleMark`, a compaction's mark at its start), taken off by `Collection.Compact` or, for a compaction in parts, `TakeStale(mark)` (only what no other compaction took off, so overlapping ones never take bytes deleted later) and never by the engine's own compactions; `Definition.Backfill{Name, Indexes, Group}`: what a collection gained after records were stored, counted once in steps (`Collection.BackfillStep`, its position in `meta/backfill/<collection>/<name>` in the same batch, so it survives a restart; a record not reached yet is counted as before, so writes and deletes meanwhile stay exact; a new database is marked done when opened, `DB.Fresh`; a backfilled index cannot be unique); nothing else builds a key), `kv/leveldb` (the goleveldb adapter, the only code importing goleveldb, checked by `kv/adapters_test.go`; goleveldb is pure Go, so the binary stays static and the image `FROM scratch`, and its files are LevelDB's format, so a LevelDB C++ adapter could read them; it is unmaintained since 2022, a risk accepted for that; another store is another adapter package plus `database/engine_<name>.go` under `//go:build <name>`, with `//go:build !<name>` on `engine_leveldb.go`), `kv/enginetest` (the test every adapter must pass), `projects` (registry). Tests open a store with `storetest.Open(t)` (a `database` in a temporary directory) and seed records with `database.Store.SaveEvent`/`SaveLogs` (for tests only, not in `store.Store`: ingest writes through `Write`); the measurements open a copy of a 60-day seed with `storetest.OpenSeed`. Ingest goes through `ingest.Pipeline` (inbox, processors, one writer that notifies after each batch). Only `main` and tests open the database.
- `notify/`: notifications.
- `api/`: the request catalog and its three transports in one package: the endpoints (`catalog.go`, `endpoint.go`, one file per area), `rest.go`, `mcp.go` with `instructions.md` and `skills/`, `ui.go` (the web app's, with its login session), `plain.go`/`plain_agents.go` (the web app's plain requests).
- `oauth/`: how agents sign in to MCP. `agentprompt/`: the prompt for coding agents, used by notify, services and the API.
- `services/`: the rules of the application (see below).
- `session/`: the login of the web app (session cookies, the login limit, form tokens).
- `fixtures/`: test data for tests only (`WebApp`: a stand-in build of the web app for full-server tests).

- `cmd/exceptic/main.go`: loads config, sets a soft memory limit of 200 MiB unless `GOMEMLIMIT` is set (`config.LimitMemory`, `config.DefaultMemoryLimit`), opens the store and runs the server of `internal/app`: `app.New` builds it from the settings, with its ingest pipeline and notifier (the tests call it too, and `App.Start` runs the pipeline of a server they serve themselves; `App.WaitStored` waits until what it accepted is stored), `app.Run` starts its pipeline and periodic jobs (`app/jobs.go`, `lanes`, logged at start as "background jobs"; a lane runs its jobs one at a time, lanes side by side; a pass that panics is logged with its stack as a failed pass ("background job failed", `logging.PanicError`) and the lane goes on (a pass that does not stop at its time limit is left running beside the lane, at most one per job; only a compaction can (the inbox compaction, the cleanup compaction, and those the size check and the project purge run), since goleveldb's `CompactRange` takes no ctx; a long pass may return `background.ErrYielded` between its steps once `background.Waiting` (another job of its lane woken or due): the lane runs those, a woken one first, then the pass again), Wakes add at most one waiting pass per job, stopped before the notifier and the store close (a pass that does not stop is waited for one second); `TestJobsStartApart` checks no two start in the same minute over a day), binds the listener before logging "server started", serves it with `config.MaxConnections` (1000) at once (`server.LimitListener`: more wait in the accept queue, idle keep-alive connections are closed when it is full) and `config.MaxHeaderBytes` (64 KiB, 431 above), graceful shutdown on SIGTERM. The `healthcheck` subcommand is what Docker's HEALTHCHECK calls (no curl in a scratch image); `reset-password [username]` (the superadmin by default) prints a temporary password, the way to recover a forgotten one (with the server stopped: `docker compose run --rm exceptic reset-password`); `backup [absolute dir]` (default `DATA_DIR/backups/<time>`; `make backup` locally, `docker compose run --rm exceptic backup` in Docker) (`backup.go`) asks the running server over its control socket (`internal/server/control.go`, `server.ListenControl`, opened by `app.Run`, `DATA_DIR/control.sock`, mode 0600, closed before the store) to write a backup, or opens the database itself when no server answers; `version` prints the build version; any other argument prints the usage (exit 2) instead of starting the server.
- `internal/platform/config`: everything comes from env (`APP_NAME` (default "Exceptic": the sidebar, page titles, login, emails, the MCP server's title and instructions, `<name> MCP: get_issue …` in notifications and the issues' "Copy for agent"; `config.AppSlug` turns it into the name agents register (`acme-errors`), with `exceptic` when no Latin letter or digit is left; the database directory is fixed, `DATA_DIR/leveldb`, so renaming the app keeps the data), `PORT`, `DATA_DIR`, `LOG_LEVEL`, `LOG_FORMAT` (`internal/platform/logging`: `auto` = pretty, colored lines in a terminal, fields one per line for settings (`logging.Block`, used by the startup records) or when a line is wider than the terminal (`NO_COLOR` turns colors off; a message or value with control characters is quoted, so logged input cannot forge lines or send terminal escapes), logfmt text elsewhere such as Docker; or `pretty`/`text`/`json`), `PROJECTS`, `ALLOWED_ORIGINS`, `RATE_LIMIT_EVENTS_PER_MINUTE`, `RATE_LIMIT_LOGS_PER_MINUTE` (`RATE_LIMIT_PER_MINUTE`, which counted envelopes, is ignored and main warns), `API_TOKEN`, `ALLOWED_IPS`, `TRUSTED_PROXIES`, `ADMIN_USERNAME`, `ADMIN_PASSWORD`, `SESSION_LIFETIME` (default `1d`, how long a login lasts; not extended by use), and the notification settings in `notifications.go`: `PUBLIC_URL`, `SECRET_KEY`, `SMTP_*`, `EMAIL_FROM`, `NOTIFY_RETRY_FOR`, `NOTIFY_KEEP_SENT`, `NOTIFY_KEEP_FAILED`; log levels to record in `recording.go`: `RECORD_LOG_LEVELS` (default all; `nil` list = every level, empty = none; events of every level are always stored), and `NotifyLevels` (fatal, error), what a new notification connection sends; the size limit in `retention.go`: `MAX_DATABASE_SIZE` ("2GB", at least `MinDatabaseBytes`, 500 MB, 0 turns it off), with the fixed numbers of the cleanup (`CleanupStartPercent`, `CleanupStopPercent`, `CleanupFilesPercent`, `CleanupAge`, `CleanupRecentAge`, `OldEventsPerIssue`) and `LogsPerMessage` (the copies of a repeated log message kept when logs are written) and `EventsPerIssuePerMinute` (10, the events an issue stores a minute; `RATE_LIMIT_EVENTS_PER_MINUTE`, default 10000 like logs, is only a guard against abuse); the fixed size limits of what ingest stores in `ingest.go` (`MaxLogBodyBytes` 16 KB, `MaxLogAttributes` 64, `MaxLogAttributeBytes` 4 KB, `MaxEventStringBytes` 16 KB, `MaxEventBytes` 1 MB, `TruncatedBreadcrumbs` 10; `docs/configuration.md`, Size limits); list values in env are comma-separated strings, parsed once here into slices; `SECRET_KEY` is trimmed as `secret.key` is, and a `PUBLIC_URL` with a user, query or fragment stops the start, `checkPublicURL`). `Notifications.ChannelAvailable(type)` says whether a connection type can be created and what is missing (email needs SMTP, Telegram/Slack need the secret key, which the server always has; unknown types are refused). `Load()` wraps `loadFrom(getenv)` so tests inject a map instead of touching the process env. `config.Projects` has `Find(idOrName)` and `ByID(id)`; use them instead of looping over projects. Code that needs the projects takes a `config.ProjectList` (`List()`) and asks on every use, because projects change while the server runs; a fixed `config.Projects` satisfies it in tests.
- `internal/storage/store` and `internal/storage/database`: the records and their rules are in `store`; `database` stores them on the `kv` layer, every collection declared once in `database/schema.go` (keys, indexes, byte counters). `database.Open(DATA_DIR)` opens `DATA_DIR/leveldb`; the running server holds it, so `reset-password` runs with the server stopped. `Store.Backup` (`database/backup.go`) copies a snapshot key by key (`kv.Copy`) into a new engine in a temporary directory inside the target, with `secret.key`, and renames the database into place last, so a backup is whole or absent while writes go on (the cleanup by size does not start meanwhile); `BackupStopped` does the same with the database opened read-only. There are no migrations: the format is recorded (`storeFormat` in `database/store.go`), and a database of another format, or without one, is refused at start with a message to move it away; a compatible change is a new collection or a field read with a default.
  - IDs: users, agents (grants), notification destinations and connections, and issues have 8 random characters `[a-z0-9]` (`store.NewID`, checked free in the batch that writes the record; `store.ValidID` refuses anything else before a lookup, routes answer 404). A project added in the web app gets a random 8-digit number (its id is in the DSN; `PROJECTS` sets its own). Event and log ids are sequence numbers (API cursors), outbox ids too.
  - Rules kept by indexes and batches: usernames unique in any case and one superadmin (unique indexes of `user`), one personal token per user, a refresh token of a client (`grant` indexes), project name and key unique; deleting a user removes their sessions, codes and grants in the same batch, deleting a connection its queued messages, deleting a project its place in connections and users' access (`dropProjectFromUsers`; an emptied list stays limited: no project), a project created by a limited user joins their access in the same batch (`CreateProject`'s owner), then its issues and logs in batches (`PurgeProjects`; `DeleteIssues` spreads a large issue's events over batches of 2000, each going on after the last event deleted, its record in the last); deleting logs (`DeleteLogs` by id, looked for under every level since a log's key starts with it) goes in batches of 2000 too. A batch reads stored keys only (`kv.Batch.Iterate`), so deleting while walking is safe.
  - Users: salted PBKDF2 `password_hash` (`pbkdf2-sha256$iterations$salt$key`, `services.hashPassword`) kept beside the user, never returned with a `store.User`, only by `FindLogin`/`UserPassword` where a password is checked; what each role may do is the methods of `store.User`: `CanAdminister`, `CanManage` (the hierarchy: the superadmin every other user, an admin users of the role user, nobody themselves there), `CanAccessAgentsOf`, `AssignableRoles` (an admin gives user only; `get_session`'s `assignable_roles`, which RoleChoices offers), `CanGiveAccess`, `CanChangeAccessOf`, `CanTakeOver` (rename, delete, reset the password, change the role, reach their agents (`CanAccessAgentsOf`): only of a user whose projects the viewer all has, `CoveredBy`), `Actor`. Project access: `store.Access` (`access.go`) on the user, its zero value every project (so users stored before it see all; no migration), else `Limited` with `ProjectIDs` (empty: none); `User.ProjectAccess()` is all for the superadmin whatever is stored; its methods (`Sees`, `SeesEach`, `Covers`, `ChangeableBy`, `Restrict` (narrows a list's project filter in place, false when nothing can match), `Visible`, `Shown`, `Replace`) are every access rule, and the `User` methods above use them. `UpdateUser` takes a `store.UserChange` with the viewer's access `By`, checked in the batch: a new name or role only when `By` covers the user (`ErrTakeOverLocked`), and `Access` merged (`Access.Replace`: the viewer's projects as chosen, the user's others kept; `ErrAccessLocked` when a limited viewer gives all or changes a user with all), so two limited admins saving one user keep each other's part. Sessions are keyed by the hash of the cookie.
  - Issue status changes: from, to, the actor (user id and name kept; source ui/mcp/api/event/expiry) and `event_id` of a reopening event; `SetIssuesStatus` records only real changes, the ingest write (`database.Store.Write`) records a regression.
  - Bounded ignore (`IgnoreIssues` with `store.IgnoreBound`: `For` one of `store.IgnoreDurations`, `Events` up to `MaxIgnoreEvents`): the issue keeps `IgnoredUntil` and `IgnoredUntilCount` (EventCount to reach, so events over the cap count too); any other status or a new ignore replaces them. No job: reads apply `Issue.At(now)` (lists, counts, `UnresolvedCounts`, get), so an issue past its time is unresolved at once, and `IssueStatusHistory` shows the pending end (source expiry, at `IgnoredUntil`); the next event or status change stores it (`batchWriter.expireIgnore`). The event after the time, or the one reaching the count (source event with its `event_id`), reports `Regression` and notifies as one. The cleanup's "resolved and ignored" step walks the stored statuses but reads each issue through `Issue.At(now)` too, so an ignore past its time counts as unresolved there and keeps its events.
  - Notification destinations (an email address, lowercase, with `Verified`/`VerifiedAt`/`VerifySentAt` (`store.Destination`) and the code hash, expiry and attempts (`destinationRecord`); or a chat with its encrypted secret) and connections (a rule: name, destination, all projects or their ids, levels, active; reading one fills the destination fields). A connection needs a confirmed destination; deleting a connection keeps an email destination, so a confirmed address stays confirmed, and deletes a chat's with its secret; a connection left without projects by a project's deletion is turned off. The outbox channel of a message is its connection's id; a message records the projects it is about (`OutboxMessage.ProjectIDs`, a summary's of every notification it stands for; none in rows stored before, seen only with every project), and `OutboxFilter.Access` keeps those all within an access (`Access.SeesEach`).
  - `first_seen`/`last_seen` use the server receive time, not the SDK clock; the times of events and logs are the SDK's, moved by the device's clock drift when the envelope's `sent_at` is a minute or more from the receive time (`ingest.clockDrift`, applied in `parseItems` (`items.go`, called by the pipeline's processors) by `sdkTime`, which replaces a time more than 30 days before or a minute after the receive time, as Sentry's Relay does: milliseconds sent as seconds would otherwise reach years JSON cannot encode; the event page says how far the clock was off, `services.ClockDrift`). `Write` reports `NewIssue`/`Regression` per event (`store.SaveResult`) (a resolved issue that happened again goes back to unresolved; ignored stays ignored until its bound ends) for notifications. An issue stores at most `Envelope.EventsPerIssue` events a minute of receive time (`config.EventsPerIssuePerMinute`, 10, set by the pipeline; zero for `SaveEvent`, so seeds store all; `batchWriter.overCap`, against the counts of stored events in `Store.minute`): the others count in `EventCount`, `LastSeen`, level and title as if stored, add to `Issue.NotStored` (persisted, `not_stored` in `issueOutput`, beside `stored_events`, `Issue.Stored`, which the issue page's events card compares its rows with, "Not stored" in the issue page's facts) and report `SaveResult.NotStored`; a new issue's and a regression's event are always stored; the counts are in memory on the store (`Store.minute`, `minuteCounts`: only the issues written to in the current minute, reset by a restart), and `Stored`/`EventDays` count stored events only.
  - Issues are read through the database, never all held in memory (format 2): the `issue` collection has a unique `fingerprint` index (project, fingerprint) for ingest, sort indexes `seen`, `first` and `count` keyed (status, project, level, value, id) (`issueSortKey`, `statusRank`, `levelRank`), `expiry` (ignores ending at a time) and record counts per (project, status, level) (`issueTally`, `kv.Definition.Tally`), all kept exact by the writes and checked by `Verify`. A list (`issue_reads.go`, `walkIssues`) merges with `kv.Merge` the prefixes the tallies say hold issues (`issuePrefixes`; an ignore whose time has passed is stored ignored and reads as unresolved, so the unresolved filter walks the ignored prefixes too), in the sort's index and direction (by project: projects by name, last seen within each), keeps what `matches` accepts (text, dates; `anyEventInRange` for a range that cuts a day), pages at most `store.LogCountLimit` deep and stops at `config.LogSearchTime`; `CountIssues` answers from the tallies without text or dates, else walks, both stopping at the limit (`more`, the pager's "+"; the menu's unresolved count, `services.Issues.Unresolved`, sums `UnresolvedCounts`, exact); `UnresolvedCounts` and `IssueLevels` come from the tallies, `GetIssue` is a point read. The writer reads an issue through its batch (`writer.issue`, `readIssue`, `findIssue` by the fingerprint index), once per batch (`peeked`); the cap of events an issue stores a minute is `Store.minute` (`minuteCounts`), the issues written to in the current minute only. The cleanup walks the issues through the sort indexes (`eachIndexed` with an `issueWalk`: the index, the statuses and where the walk can stop, oldest first, merged over the tallies' prefixes and resumed from its position by `kv.Query.FromRest`: step 3 `first` oldest first up to a month, step 4 `seen` over resolved and ignored, `deleteUnseen` by `seen` oldest first; step 7, `trimCopies`, walks the sparse `trim` index (project, stored, id: only issues storing more than `OldEventsPerIssue`, backfilled as `trim` on older databases) from its top at every batch, so no issue whose count grows between batches is passed over, `TestTrimCopiesFollowsGrowingIssues`; `cleanupPositions` in the order hash ends a run whose saved position means something else now).
  - Logs and events are read newest first through their indexes; time marks (`marks.go`) turn date ranges into sequence ranges. Text search of logs compares each line (`textutil.ContainsFold`), first on the stored bytes when the text has no character JSON escapes (`rawSearchable`), so most lines are never decoded; a count that the index walks answer exactly counts keys (`countByKeys`); log counts (the pager) stop at `store.LogCountLimit` (10000; `CountLogs` returns `more`, the pager shows "of 10000+"). A walk over the logs (`scanLogs`; not a count by keys) stops at `config.LogSearchTime` (20 s, every request alike, by the store's clock, `searchBudget`) and reports a `store.LogScan`: `Rest` (logs below it not searched; `merged` steps every walk key by key, so one bound holds for all) and `SearchedTo` (every log received since was searched, from the time marks); a count gives `FromID`, the oldest match or where it stopped, which bounds its list (`LogFilter.FromID`).
  - API lists fetch `limit+1` rows; `store.Page` trims them and says whether a next page exists (cursor pagination). The web app's lists use pages (`Offset`/`Limit` of `IssueFilter`/`LogFilter`, the API's offset cursor); issues and logs by walking indexes newest first.
  - `store` never imports `sentry`: callers map to `NewEvent`/`NewLog`.
- `internal/server`: `net/http` ServeMux with method patterns (`"GET /health"`), wrapped in a request-logging middleware (its `statusRecorder` unwraps, so `http.ResponseController`, the read deadline of ingest bodies, reaches the connection) and `recoverPanics` inside it: a handler's panic is logged with method, path, route and stack and answered as a JSON 500 "internal error" (the connection is dropped if the answer had begun). Built from `server.Options`; depends on small interfaces (`Pinger`, `http.Handler` for ingest, `Routes` for the API and the web app), so tests use fakes. Mounts ingest (open), `/health` (open; 503 when `Store.Ping`, a read of the store, fails), the links that stop emails (`Unsubscribe`, open, signed), the API wrapped in `protectAPI` (IP allowlist first, then API token); MCP, OAuth, the web app (`Web`, every address no other route takes) and its API (`UIAPI`, a `UIRoutes`: routes plus the handler of every other address under `UIAPIPrefix`) use the IP allowlist plus their own authentication. `RESTPrefix` (`/api/v1/`) and `UIAPIPrefix` (`/api/ui/`) are defined here; the one `"/api/"` fallback (`unknownAPI`) sends `/api/ui/...` to the web app's API (a login, then a JSON 404) and anything else to a JSON 404 behind the token. `headers.go`: `ContentSecurityPolicy` (the one builder: script sources such as the page's inline hashes), `SecurityHeaders` (policy, nosniff, `Referrer-Policy: same-origin` (no-referrer would make browsers send `Origin: null` on same-origin POSTs), `X-Frame-Options`), `SameOrigin` (Origin's host is the request's, and https when the request is (`IsHTTPS` with the trusted proxies); oauth compares with PUBLIC_URL on purpose), used by `web` and `api/ui.go`.

Decoding is deliberately lenient: custom types (`Timestamp`, `Message`, `Tags`, `ExceptionList`, …) accept every shape the protocol allows and fall back to the zero value on an unexpected one, because losing a field is better than losing the error report; every other field goes through `Decode` (`decode.go`, also used for the request, contexts and breadcrumb data by the issue page (`services.Issues.Details`) and the agent prompt): a plain decode first (`ExceptionList`/`BreadcrumbList` strict in it), and only when it fails one walk over a `jsontext` token stream (one more pass however deep the field, `TestWrongTypedFieldCostsLittleMore`), where numbers and booleans fill string fields as their text and objects or arrays leave them empty (like Relay's `LenientString`; `release: 5`, `lineno: "12"`), booleans count only as JSON booleans (as ingest's `isAppFrame` reads `in_app`), and list elements or map values of the wrong shape are dropped one by one, so an odd frame keeps the rest of the exception chain. Only a payload that is not a JSON object (`null` included) fails `ParseEvent`/`ParseLogs`. `Event.Raw` keeps the full payload; `Event.Trace()` gives trace and span IDs; `NormalizeEventID` turns UUID form into 32 hex. `Timestamp` leaves a time JSON cannot encode (years outside 0–9999, e.g. milliseconds sent as seconds) zero, so breadcrumb times never fail an output.
- `internal/ingest/grouping`: decides which events are one issue. Custom SDK `fingerprint` wins (`{{ default }}` expands to the default; `variables.go`: the variables of Sentry's Fingerprint Rules with their aliases, only as a whole value, `<no-…>` when empty (`<no-value-for-tag-NAME>`), message and error value normalized, stack ones from `crashFrame` (Sentry's: newest in-app frame of the outermost error), `{{ tags.NAME }}` with the tags Sentry derives before grouping (`tagValue`); unknown ones stay literal; the list is in `docs/sdk.md`). Messages group by `sentry.Event.MessageTemplate` (logentry's or message's `message`) when sent, else the text. JS family (platform javascript/node or a JS-like file) compares a function by its last name after a dot, without `at `/`new ` (`javaScriptFunction`). A source line over 120 characters does not count (`sourceLine`), on every platform (Go sends source too, so no platform list). An exception group (`Mechanism.IsExceptionGroup`, `exception_id`/`parent_id`; `exception_groups.go`) is grouped by its tree: each group's distinct children sorted, a top-level group of one distinct child is that child; ids that only loop fall back to the chain as sent. Default: exception chain types + in-app frames as file/module + function + source line (`context_line`), no line numbers; events with the same fingerprint in one project are one issue, every exception of the chain adds its type and its frames (the in-app ones when there are any, otherwise all frames after the async boundary); line numbers are left out so a deploy that shifts code opens no new issue, and the source line keeps two throws in one function, or two functions with the same name, apart; in-app is `sentry.Frame.IsInApp`: marked by the SDK and not under `node_modules/` (a browser SDK marks every frame of the page's origin in-app, and Vite serves libraries from there as `/node_modules/.vite/deps/`), and only frames after the newest async boundary count (a function with `*`, as Firefox and Safari mark it, e.g. `promise callback*queueFlush`), so the path that scheduled the callback does not split one error into several issues (JS names `handler: () => {}` after the property, so the function name alone merges unrelated errors); anonymous functions without source use the line number; file and module paths drop origins, query strings (`tsx watch` adds `?<timestamp>`) and bundle hashes (8+ hex characters after `.`, `-` or `_`: webpack, Next.js, Turbopack; 8 base64url characters after `-` or `.` that only extensions follow, the one nearest the end: Rollup 4/Vite 5+, SvelteKit, Astro; only with a digit or an uppercase letter after the first character, so `use-settings.js` and `user.reducers.js` stay and an all-lowercase hash, about 1 in 400, opens a new issue); if the newest grouping frame has no source line that counts (browser, or over 120 characters), the normalized error text is added. An exception without frames adds its normalized value instead; messages (and `captureMessage`'s exception without a type) group by their normalized text, so "order 890" and "order 891" match. These rules and `docs/sdk.md` (Grouping) are the one description of grouping; change grouping only with tests, because a change regroups new events into new issues.

- `internal/notify`: alerts about new and regressed issues (the ingest write reports them; `StoreSink` calls `Notify` with the project id). Delivery goes through the outbox (collection `outbox`), so it survives restarts and outages:
  - `Notify` only queues in memory and never blocks ingest; it cuts the title and culprit to what an issue keeps (`store.MaxTitleLength`, `MaxCulpritLength`) and environment and release too. A dispatcher goroutine reads the connections (once per burst: again whenever its queue has emptied), sends each notification to those that match (one outbox batch for all of them) (`matches`: active, verified, project, level; unknown levels count as errors), applies the flood limit per connection (5 per minute individually, the rest as one `Summary` when the window ends; a window keeps only the count and the first `maxSummaryItems` held notifications, so a flood of large events does not pile up in memory) and writes outbox rows.

A failed send ends its pass and waits for its retry, so later messages overtake it (one message the channel refuses does not hold back the rest for `NOTIFY_RETRY_FOR`); a `RetryAfterError` pauses the worker for its delay (only while the message is retried, so never past `NOTIFY_RETRY_FOR`; a Retry-After beyond it fails the message and pauses nothing); a send that panics fails its message at once (stack only in the log, `sendOrFail`), a panic while routing drops that notification (`routeOrDrop`); a message sent while the store refused to record it is not sent again (`worker.unmarked`, recorded on the next pass). The channel is rebuilt from the stored connection for every batch of due messages, so edits apply to queued messages; a disabled or deleted connection fails them (`errGone`). Retries follow `Schedule` (2s, 10s, 30s, 1m, 5m, 15m, 30m, then hourly) until `NOTIFY_RETRY_FOR`; `RetryAfterError` carries a channel's own rate-limit delay. Saving an active connection makes its waiting messages due at once (`store.RetryOutboxNow`, called from `services.Connections`), and ends a rate-limit pause (`Notifier.RetryNow`, given to services as `services.Dependencies.Notifier`; `app.New` builds the notifier before the services), since a save is usually the fix; `services.Connections.RetryNow` does the same without a save; both wake the connection's worker (starting one if none runs), so it sends them at once instead of at its next poll. A removed value becomes `[Filtered]` (`filteredText`, `%5BFiltered%5D` inside URLs); only values change, the rest stays byte for byte. Strings (`scrubText`): one that is a JSON object or array (a request body sent as text) is scrubbed by the payload's rules (`scrubJSONText`, one level: its own strings are free text, `TestNestedDocumentsInTextStayLinear`); free text (`scrubFreeText`) loses PEM private key bodies (BEGIN/END lines kept), the tokens chat services put into URL paths (`textutil.ReplaceServiceTokens`, shared with `agentprompt`: Telegram `bot<id>:<token>`, Slack `/services/…`, Discord `/api/webhooks/…`), the values of multipart form fields with a secret's name (`scrubMultipart`), the values of `"key": value` and `'key': value` pairs (`scrubQuotedPairs`: strings, numbers, and arrays or objects by one bracket count that skips strings, `collectionEnd`), the credentials of authorization schemes (Bearer, Basic (also `user:password`), Token, ApiKey, Digest, AWS4-HMAC-SHA256, Negotiate, NTLM; a token, not a word or a pair: `isSchemeToken`, after `token` 16+ characters with a digit, so `Unexpected token NumericLiteral` stays) and of curl's `-u`/`--user`, unquoted `key=value`, `key: value` and `key => value` pairs (`scrubKeyValues`: logfmt, env dumps, connection strings, header lines (Authorization keeps its scheme, Cookie its harmless cookies), the reprs of Python, Ruby, PHP, Java, Go, Node, GraphQL arguments; a key quoted, `[bracketed]` or escaped at any depth, so JSON encoded in JSON on any level or a body encoded twice is caught by its `\"key\": \"value\"` (`escapedQuote`, at most 64 backslashes); after `key: ` with a space the key must open a field (or the value be quoted) and the value look like a token (`looksLikeToken`: hyphenated lowercase names are words), so `Invalid token: expired` stays; an unquoted value also stays when it is a literal (`null`, `true`), a number of under 6 digits under a name that holds no numbers (`namesNumericSecret`: `session: 401`, `pass=118`, but `pin: 1234`), followed by prose after a spaced separator (`token: 3 retries left`), or a line number after a file name (`token.ts:42:13`); ends of values and lines are searched once per scan (`nextIndex`), so refused header lines in quotes stay linear), in URLs (absolute, relative such as `GET /reset?token=… 200`, bare query strings, each found inside text, nested ones in a query included) the userinfo password (it may hold `/?#@`; the user stays) and the parameters of the query, fragment and path (`;jsessionid=`) whose name names a secret or is `code` or `key` (`credentialParameters`, not in a bare `code=ERR_NETWORK` of one pair), and card numbers (13 to 19 digits, grouped or not, network length and Luhn; also JSON numbers). SDKs with `sendDefaultPii` send request cookies and the `Authorization` header, so the rules apply to every part of a payload. It is one pass over the JSON tokens (`encoding/json/jsontext`, `scrubValue`/`scrubObject`/`scrubValues`), no tree; only an array led by a secret's name is read as a tree, so deep nesting stays linear (`TestDeepNestingStaysLinear`); every text scan is one pass with bounded look-back (`*StayLinear` tests in `prepare_test.go`). Bare tokens without a key name stay (the agent prompt masks them, `agentprompt.Redact`). Data stored before it existed is not rewritten.
- Levels to record: events (errors and messages) of every level are stored (issues group them, notification connections filter by level, SDKs filter noise themselves); only logs are filtered: each project may set its own log levels (`Project.LogLevels`; nil = the `RECORD_LOG_LEVELS` default, an empty list = none, kept apart through JSON by `keepNone`; the form stores the default as nil (`chosenLevels`) so a project follows it). `StoreSink` stores levels under their canonical names (`config.EventLevel`: critical = fatal, warn = warning, log = info, trace = debug, unknown = error; `config.LogLevelOf` for logs: a missing or unknown level from `severity_number` by the OpenTelemetry ranges, else info; `sentry.ParseLogs` leaves `Level` as sent), so filters, notifications and badges never translate them again, and drops logs of levels not recorded before storing.
- `internal/ingest`: `POST /api/{projectID}/envelope/`. Order matters: CORS → public key (query `sentry_key`, `X-Sentry-Auth`/`Authorization`, or the envelope header `dsn` when sent via a tunnel: only the first line is decompressed for it (a br body, which can only be read whole, is refused there with 401: only sentry-python sends br, always with the key in the request), `requestBody.header`, at most `MaxHeaderBytes`, its buffer growing as bytes arrive; with the key in the request nothing of the body is read before project auth) → project auth (the first request with the key marks the project connected: `database.Store.MarkContact`, collection `project_contact`, written once, then only an in-memory check, `FirstContact`; whatever the items, a session at the SDK's start too) → read/decompress body (gzip, deflate, br (sentry-python); 20 MB cap before and after decompression; all bodies being read share `MaxReadingBytes`, 80 MB, one project at most half of it (`readBudget`, counted as the buffers grow, a br body is read whole first, then the window its stream declares (up to 16 MB, which the decoder may fill before any output) is held while it is decoded in memory, so a stalled client holds only the bytes it sent; 429 with `Retry-After` beyond it), and a body must arrive within `BodyReadTimeout`, 10 s, else 408) → parse the envelope; one without `event` or `log` items gets 200 at once, neither counted nor stored (`storesItems`: spans, sessions and client reports are never limited) → the per-project rate limits (`limits.go`, `rateLimiter`, in memory, one fixed calendar-minute window per project of the registry: `RATE_LIMIT_EVENTS_PER_MINUTE` counts event items, `RATE_LIMIT_LOGS_PER_MINUTE` the logs of log items (`logsInItem` counts the `items` array, never the SDK's `item_count`; a log item without logs counts once); an item that does not fit is dropped whole and its category stays closed until the minute ends; the envelope goes on without the limited items (`withoutLimited`, `sentry.Envelope.Encode` keeps the header lines as sent) with 200 and `X-Sentry-Rate-Limits: <seconds>:<categories>:project` naming only the limited ones (`error;default;security` for events, as the JS SDK maps every event item to `error`; `log_item` for logs), so the SDK pauses only them; nothing left to store is a 429 with the same header and `Retry-After` (unlike Relay, which answers 429 to a partly accepted envelope too); what the inbox refuses is taken back (`refund`); the first limited envelope of a category in a minute logs one warning (`warnLimited`); only the busy answers (inbox full, read budget, a compaction part: `errCompacting`, `Retry-After: 5`) send `<seconds>::project`, every category) → the inbox (`Pipeline.accept`: the envelope as it came (or as `Encode` rebuilt it), with the project and the receive time; 429 above `config.MaxInboxBytes`, 20% of `MAX_DATABASE_SIZE` (of its default when the limit is off), so a backlog can never crowd out stored data) and the answer. The queues to the processors carry an entry's sequence, project and size only (`Pending` reads no bodies); a processor reads the body (`InboxBody`, a slice of the engine's copy, `kv.Collection.GetValue`, so one copy, `TestInboxBodyCopiedOnce`) once its bytes fit `ParseBytes` (32 MB for the envelopes being parsed or waiting for the writer, freed when stored), and an entry already stored gives nothing, so one handed both from the fresh queue and by a scan of the inbox is stored once (`TestScanDoesNotStoreTwice`). A processor then runs `scrubJSON` on every log item and, for events, `prepareEvent` (`compactEvent` over the token decoder and encoder of `scrub.go`, one pass, then `truncateEvent`; `prepare_test.go` checks, also as a fuzz target, that it gives what the tree pass it replaced gave) → parse all items → the writer's batch, which also deletes the inbox entry (a batch failing on a record JSON cannot encode is written one envelope at a time and that envelope is dropped, `storeBatch`, since no retry would fix it); an entry whose processing panics is logged and dropped from the inbox (`processOrDrop`), and a panic while reporting a stored event loses only that report. All items are parsed before anything is stored, so a malformed item (not JSON, or not an object) drops the whole envelope. Only `event` and `log` items are stored; other types are dropped. `NewPipeline` builds the handler with its pipeline, so every envelope, the tests' too, goes through the inbox. `StoreSink` computes the grouping fingerprint, maps Sentry types to `store.NewEvent`/`store.NewLog` and reports what the writer stored (log lines, notifications). Rejections are logged at debug level (ingest is public, so warn-level logging would be a flood vector). `DropCounter` (`dropped.go`, `Pipeline.Dropped`, built before the services in `app.New`) counts per project, in memory, in hourly buckets of 24 h, what was refused after the key check (`countRefused`: rate limit by category, busy (429, a store failure), too large (413), invalid (400, 415), incomplete (408, or the client hung up: `requestError.incomplete`); items once parsed, else envelopes) and what `client_report` items say the SDK dropped (`sentry.ParseClientReport`; ratelimit_backoff, queue/buffer/cache overflows and backpressure; sampling, `beforeSend` and `network_error`/`send_error` not: SDKs report the server's refusals that way too, so they would count twice), with one warning per project an hour; reasons and their texts are `store.DropReasons`.

### Projects and DSNs

`PROJECTS=1:backend:<key>,2:frontend:<key>` — `id:name:public_key`, seeded into the database at every start (more projects can be added in the web app, see `internal/storage/projects`). IDs are chosen by the user and must stay stable: the id is part of the DSN (`http://<key>@host:8000/<id>`) and is stored with every event, so it must never be derived from list order. Each service (backend, SSR, frontend…) gets its own project; all live in one container and the web app shows which project an error came from. The Projects page shows each DSN: at `PUBLIC_URL` when set (path prefix kept), else at the address the web app was opened with (https behind a trusted proxy that sends `X-Forwarded-Proto`). The scheme is part of the DSN; SDKs cannot parse one without it.

Auth model: users with roles (the superadmin from env at the first start, the others added in the web app) and an API token, plus an IP allowlist for the web app, MCP and the API; the ingest endpoint stays open (protected only by DSN keys, CORS `ALLOWED_ORIGINS` and rate limiting) because browsers send errors directly.

## Conventions

- Tests sit next to the code (`*_test.go`, same package unless they drive the whole server); fixtures go in `testdata/`. When adding a check, make sure the test fails without the fix.
- Blank lines (enforced by `wsl` in `.golangci.yml`, same rule as the team's TypeScript projects): always a blank line before `if`/`for`/`switch`/`defer`/`return`, including `if err != nil` right after the call; consecutive assignments stay together. Run `make fix` after editing; `--fix` only adds blank lines, it never removes extra ones.
- Everything in the repo is in English: code, comments, test data, interface text. Test values are plain and conventional (`root` / `root-password`, `admin`), not invented strings in other languages.
- Use descriptive variable names (`settings`, `database`, `batch`, `connectionList`), not one-letter ones. Keep the standard Go idioms `err`, `ctx`, `t`, and `w`/`r` in HTTP handlers.
- Do not copy code from Bugsink (PolyForm Shield license) or Sentry (FSL). GlitchTip (MIT) is fine as a reference.
- Commit messages: one subject line containing `DevFo-OSS/17`, no body, no AI attribution. Commit only when asked.
- `skills/exceptic/SKILL.md`: the Agent Skills skill for users' coding agents (`npx skills add devforth/exceptic -g`, or `~/.claude/skills/`, `~/.agents/skills/`): deploy, connect MCP, connect an app, investigate. It holds the workflow and safety rules and links the docs by raw GitHub URL instead of repeating them; a change to a documented step updates the doc, and the skill only when the workflow changes.
- The web app (`web/`): every element that looks or acts the same is one Svelte component; pages compose components and never repeat markup or long class strings; a new look is a prop or variant of the existing component, shown on `/design-system` (and in the design artifact) in the same change.
- Field hints come only from `docs/ui.md` and `docs/configuration.md` through the generated `help` (see `web/`); never write a hint's text in a component.
- Docs: the README is short (features, quick start, one SDK example, links); user docs are in `docs/` (`deployment.md`, `configuration.md` with every env var, `ui.md` with the fields of the settings pages, `sdk.md`, `mcp.md`, `api.md`) and `docs/sentry-protocol.md` is research notes. A new or changed env var, subcommand, API route or MCP tool updates its doc in the same change, and `.env.example` too.
