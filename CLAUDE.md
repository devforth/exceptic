# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Lightweight self-hosted error and log monitoring server that accepts data from the official Sentry SDKs via DSN (envelope protocol). Go, an embedded key-value store (goleveldb, pure Go, no CGO), shipped mainly as a Docker image (`FROM scratch`, size budget 50 MB, currently ~20 MB, ~6 MB to pull). MIT, public DevForth OSS project. Tracklify task: `DevFo-OSS/17`.

Scope: errors and logs only. Tracing spans, session replay, uptime and `client_report` items are accepted and dropped, not stored.

Stages: 0 protocol research, 1 skeleton, 2 ingest, 3 data model and grouping, 4 REST API, 5 UI and 6 notifications (Slack and Telegram short, email full), 7 retention (now cleanup by size), 8 packaging and docs, and 9 MCP are done, plus users with roles and the issue status history. The web UI is a SvelteKit SPA (`web/`), which replaced the server-rendered htmx UI. Next: the first release (tag `v0.1.0`), per-project disk shares, Google sign-in.

## Commands

Go is installed in `~/.local/go`; if `go` is not on PATH, run `export PATH="$HOME/.local/go/bin:$HOME/go/bin:$PATH"` first.

```sh
make test         # go test -race ./...
make lint         # golangci-lint (.golangci.yml): vet, staticcheck, errcheck, gofmt/goimports, wsl blank lines
make fix          # auto-fix formatting, import order and blank lines; run after editing Go code
make build        # static binary to bin/exceptic
make docker       # build image devforth/exceptic:dev
make image-size   # fails if the image is over MAX_IMAGE_MB (50)
make web          # build the SPA (web/, Node 24 + pnpm) into web/dist/spa, which Go embeds; make build runs it
make web-check    # svelte-check, prettier --check, eslint, vitest
make api-types    # rewrite web/src/lib/api/catalog.gen.ts from the catalog; make test fails while it is stale
make dev          # the user runs it: everything at :8000 in one terminal, the app with hot reload (Vite) and the Go server behind it on :8001 (Ctrl+C stops both)

go test ./internal/storage/database -run TestUserRules -count=1   # single test
go test ./web                                                     # checks a built SPA page against what Go expects (skipped when not built)
```

Do not start the server (`make run`, `docker run`, …) yourself; the user runs it in their own terminal. Check it with `curl localhost:8000/health` and ask the user to start it if it is not reachable. `make run` loads `.env` and `.env.local` (gitignored; template in `.env.example`); without projects (`PROJECTS` or added in the web app) every event is rejected: the start logs a warning, each rejected envelope only a debug line (`LOG_LEVEL=debug`). `.env.example` holds placeholders only; the real keys and passwords go into `.env.local`. `go run` does not rebuild on change: after editing Go code (or rebuilding the web app, which is embedded), the user must restart it; `make dev` (`tools/dev.sh`) runs the server and the app with hot reload in one terminal.

The image has a writable `/tmp` (scratch has none). CI (`.github/workflows/ci.yml`) runs golangci-lint (pinned version), `make test`, `make web-check web` with `go test ./web`, an amd64 image build with the size check and an arm64 build. `release.yml` runs on a `vX.Y.Z` tag: it calls `ci.yml` (`workflow_call`), then pushes `devforth/exceptic:X.Y.Z`, `:X.Y` and `:latest` (not for pre-releases) for amd64 and arm64 to Docker Hub (secrets `DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN`). `compose.yml` is the example deployment the docs refer to.

## Architecture

Where to look first:

| What | Where |
|---|---|
| Startup, shutdown, subcommands | `cmd/exceptic/main.go`; the server built and run by `internal/app` (`app.New`, `app.Run`), the same wiring the tests use |
| Every periodic job and its lane | `internal/app/jobs.go` (the database lane: `database.Store.Lane`); the runner `internal/platform/background` |
| Schedules, time limits, size limits | `internal/platform/config/schedule.go`, `retention.go` |
| All settings from env | `internal/platform/config` (documented in `docs/configuration.md`) |
| HTTP mounts (health, ingest, API, the web app's API, MCP, OAuth, web app) | `internal/server/server.go`; the web app at every other address (`web/web.go`) |
| REST endpoints, MCP tools, the web app's requests | `internal/api` (one catalog entry each; `rest.go`, `mcp.go`, `ui.go`) |
| Rules of the application | `internal/services` (the only way the web app and tools reach data) |
| Storage records and their rules | `internal/storage/store`; every collection and index in `internal/storage/database/schema.go` |
| Ingest path | `internal/ingest` (handler → inbox → pipeline → `StoreSink`) |
| Notifications | `internal/notify` |
| The web app | `web/` (SvelteKit project and Go package `web`) |

`internal/` is grouped by area; a package sits in the folder of the part it belongs to:

- `platform/`: what every part uses: `background` (the lanes of periodic jobs), `config` (with the field limits and the level order, `HighestFirst`/`InLevelOrder`, and `ShownLevel`, the color group of a level in the web app and emails), `logging`, `secret`, `textutil` (`TruncateRunes`, `Shorten` with "…", `ContainsFold` (substring ignoring the case of ASCII letters, the log and issue search), `EmailLocalPart`, `Slug` (`AppSlug`, prompt file names), `IndentJSON`, `MaskSecret`, `AuthCredential` (Bearer/Basic in text, for `scrub` and `agentprompt`)).
- `app/`: the server built from its parts (`New`, for main and the tests), run with its background work (`Run`), the periodic jobs (`jobs.go`) and the backup socket's handler.
- `server/`: the HTTP shell: the routes of the whole server (health, ingest, API, the web app's API, MCP, OAuth, web app) and `/health` (`server.go`), the IP allowlist and token (`access.go`), security headers, the CSP builder and the Origin check (`headers.go`), JSON answers (`json.go`), the control socket of backups (`control.go`).
- `ingest/`: receiving from Sentry SDKs (handler, pipeline, `StoreSink`, `compact.go`, `scrub.go`) with `grouping`.
- `sentry/`: the SDK wire format, read by ingest, notify, services (the issue page) and the agent prompt.
- `storage/`: `store` (the API of the storage: the records, their rules and the `Store` interface, every operation on the records; everything else uses only it, except the inbox (`ingest.Pipeline`) and the periodic jobs and backups (`internal/app`, the database lane built by `database.Store.Lane`), which take `*database.Store`), `database` (the one implementation of that API: every record, the ingest inbox included, each collection declared in `database/schema.go`; the engine is picked in `database/engine_leveldb.go`, the only file naming it, and its data lives in `DATA_DIR/leveldb`), `kv` (the layer under it, unaware of the application: keys built from typed parts, collections with declared indexes, batches with counters and sequence numbers, queries and cursors (`Head` decodes only a record's head when the collection has `DecodeHead`, as events, the inbox and the outbox do; `Raw` filters on the stored bytes before decoding; `Count` without `Where` or `Raw` counts keys; `WithContext` ends a walk with its context), `Check` (`Schema.Check` runs it on every collection, as `Store.Verify` does), the `Engine` interface; `Definition.Group`: a second byte counter per record (the project), written in the same batch under `group/` and kept apart from `Counter`'s (not in `Batch.Counted`, `DB.Written` or the cleanup's total; `DB.Groups`); `Definition.Backfill{Name, Indexes, Group}`: what a collection gained after records were stored, counted once in steps (`Collection.BackfillStep`, its position in `meta/backfill/<collection>/<name>` in the same batch, so it survives a restart; a record not reached yet is counted as before, so writes and deletes meanwhile stay exact; a new database is marked done when opened, `DB.Fresh`; a backfilled index cannot be unique); nothing else builds a key), `kv/leveldb` (the goleveldb adapter, the only code importing goleveldb, checked by `kv/adapters_test.go`; goleveldb is pure Go, so the binary stays static and the image `FROM scratch`, and its files are LevelDB's format, so a LevelDB C++ adapter could read them; it is unmaintained since 2022, a risk accepted for that; another store is another adapter package plus `database/engine_<name>.go` under `//go:build <name>`, with `//go:build !<name>` on `engine_leveldb.go`), `kv/enginetest` (the test every adapter must pass), `projects` (registry). Tests open a store with `storetest.Open(t)` (a `database` in a temporary directory) and seed records with `database.Store.SaveEvent`/`SaveLogs` (for tests only, not in `store.Store`: ingest writes through `Write`); the measurements open a copy of a 60-day seed with `storetest.OpenSeed`. Ingest goes through `ingest.Pipeline` (inbox, processors, one writer that notifies after each batch). Ingest and `internal/app` take `*database.Store`, the rest of the code `store.Store`; only `main` and tests open the database.
- `notify/`: notifications.
- `api/`: the request catalog and its three transports in one package: the endpoints (`catalog.go`, `endpoint.go`, one file per area), `rest.go`, `mcp.go` with `instructions.md` and `skills/`, `ui.go` (the web app's, with its login session), `plain.go`/`plain_agents.go` (the web app's plain requests).
- `oauth/`: how agents sign in to MCP. `agentprompt/`: the prompt for coding agents, used by notify, services and the API.
- `services/`: the rules of the application, the only way the web app and the agents' tools reach the database (see below).
- `session/`: the login of the web app (session cookies, the login limit, form tokens), one `Auth` built in `app.New`.
- `fixtures/`: test data for tests only (`WebApp`: a stand-in build of the web app for full-server tests).

The web app is `web/` at the repo root (see below).

- `cmd/exceptic/main.go`: loads config, sets a soft memory limit of 200 MiB unless `GOMEMLIMIT` is set (`config.LimitMemory`, `config.DefaultMemoryLimit`), opens the store and runs the server of `internal/app`: `app.New` builds it from the settings, with its ingest pipeline and notifier (the tests call it too, and `App.Start` runs the pipeline of a server they serve themselves; `App.WaitStored` waits until what it accepted is stored), `app.Run` starts its pipeline and periodic jobs (`app/jobs.go`, `lanes`, logged at start as "background jobs"; a lane runs its jobs one at a time, lanes side by side (a pass that does not stop at its time limit is left running beside the lane, at most one per job; only the inbox compaction can, goleveldb's `CompactRange` takes no ctx), Wakes add at most one waiting pass per job, stopped before the notifier and the store close (a pass that does not stop is waited for one second); `TestJobsStartApart` checks no two start in the same minute over a day), binds the listener before logging "server started", graceful shutdown on SIGTERM. The `healthcheck` subcommand is what Docker's HEALTHCHECK calls (no curl in a scratch image); `reset-password [username]` (the superadmin by default) prints a temporary password, the way to recover a forgotten one (with the server stopped: `docker compose run --rm exceptic reset-password`); `backup [absolute dir]` (default `DATA_DIR/backups/<time>`; `make backup` locally, `docker compose run --rm exceptic backup` in Docker) (`backup.go`) asks the running server over its control socket (`internal/server/control.go`, `server.ListenControl`, opened by `app.Run`, `DATA_DIR/control.sock`, mode 0600, closed before the store) to write a backup, or opens the database itself when no server answers; `version` prints the build version; any other argument prints the usage (exit 2) instead of starting the server.
- `internal/platform/config`: everything comes from env (`APP_NAME` (default "Exceptic": the sidebar, page titles, login, emails, the MCP server's title and instructions, `<name> MCP: get_issue …` in notifications and the issues' "Copy for agent"; `config.AppSlug` turns it into the name agents register (`acme-errors`), with `exceptic` when no Latin letter or digit is left; the database directory is fixed, `DATA_DIR/leveldb`, so renaming the app keeps the data), `PORT`, `DATA_DIR`, `LOG_LEVEL`, `LOG_FORMAT` (`internal/platform/logging`: `auto` = pretty, colored lines in a terminal, fields one per line for settings (`logging.Block`, used by the startup records) or when a line is wider than the terminal (`NO_COLOR` turns colors off; a message or value with control characters is quoted, so logged input cannot forge lines or send terminal escapes), logfmt text elsewhere such as Docker; or `pretty`/`text`/`json`), `PROJECTS`, `ALLOWED_ORIGINS`, `RATE_LIMIT_PER_MINUTE`, `API_TOKEN`, `ALLOWED_IPS`, `TRUSTED_PROXIES`, `ADMIN_USERNAME`, `ADMIN_PASSWORD`, `SESSION_LIFETIME` (default `1d`, how long a login lasts; not extended by use), and the notification settings in `notifications.go`: `PUBLIC_URL`, `SECRET_KEY`, `SMTP_*`, `EMAIL_FROM`, `NOTIFY_RETRY_FOR`, `NOTIFY_KEEP_SENT`, `NOTIFY_KEEP_FAILED`; log levels to record in `recording.go`: `RECORD_LOG_LEVELS` (default all; `nil` list = every level, empty = none; events of every level are always stored), and `NotifyLevels` (fatal, error), what a new notification connection sends; the size limit in `retention.go`: `MAX_DATABASE_SIZE` ("2GB", at least `MinDatabaseBytes`, 500 MB, 0 turns it off), with the fixed numbers of the cleanup (`CleanupStartPercent`, `CleanupStopPercent`, `CleanupAge`, `CleanupRecentAge`, `OldEventsPerIssue`) and `LogsPerMessage` (the copies of a repeated log message kept when logs are written); list values in env are comma-separated strings, parsed once here into slices). `Notifications.ChannelAvailable(type)` says whether a connection type can be created and what is missing (email needs SMTP, Telegram/Slack need the secret key, which the server always has; unknown types are refused). `Load()` wraps `loadFrom(getenv)` so tests inject a map instead of touching the process env. `config.Projects` has `Find(idOrName)` and `ByID(id)`; use them instead of looping over projects. Code that needs the projects takes a `config.ProjectList` (`List()`) and asks on every use, because projects change while the server runs; a fixed `config.Projects` satisfies it in tests.
- `internal/storage/store` and `internal/storage/database`: the records and their rules are in `store`; `database` stores them on the `kv` layer, every collection declared once in `database/schema.go` (keys, indexes, byte counters). `database.Open(DATA_DIR)` opens `DATA_DIR/leveldb`; the running server holds it, so `reset-password` runs with the server stopped. `Store.Backup` (`database/backup.go`) copies a snapshot key by key (`kv.Copy`) into a new engine in a temporary directory inside the target, with `secret.key`, and renames the database into place last, so a backup is whole or absent while writes go on (the cleanup by size does not start meanwhile); `BackupStopped` does the same with the database opened read-only. There are no migrations: the format is recorded (`storeFormat` in `database/store.go`), and a database of another format, or without one, is refused at start with a message to move it away; a compatible change is a new collection or a field read with a default.
  - IDs: users, agents (grants), notification destinations and connections, and issues have 8 random characters `[a-z0-9]` (`store.NewID`, checked free in the batch that writes the record; `store.ValidID` refuses anything else before a lookup, routes answer 404). A project added in the web app gets a random 8-digit number (its id is in the DSN; `PROJECTS` sets its own). Event and log ids are sequence numbers (API cursors), outbox ids too.
  - Rules kept by indexes and batches: usernames unique in any case and one superadmin (unique indexes of `user`), one personal token per user, a refresh token of a client (`grant` indexes), project name and key unique; deleting a user removes their sessions, codes and grants in the same batch, deleting a connection its queued messages, deleting a project its place in connections, then its issues and logs in batches (`PurgeProjects`; `DeleteIssues` spreads a large issue's events over batches of 2000, each going on after the last event deleted, its record in the last). A batch reads stored keys only (`kv.Batch.Iterate`), so deleting while walking is safe.
  - Users: salted PBKDF2 `password_hash` (`pbkdf2-sha256$iterations$salt$key`, `services.hashPassword`) kept beside the user, never returned with a `store.User`, only by `FindLogin`/`UserPassword` where a password is checked; what each role may do is the methods of `store.User`: `CanAdminister`, `CanManage`, `CanAccessAgentsOf`, `AssignableRoles`, `Actor`. Sessions are keyed by the hash of the cookie.
  - Issue status changes: from, to, the actor (user id and name kept; source ui/mcp/api/event) and `event_id` of a reopening event; `SetIssuesStatus` records only real changes, the ingest write (`database.Store.Write`) records a regression.
  - Notification destinations (an email address, lowercase, with `Verified`/`VerifiedAt`/`VerifySentAt` (`store.Destination`) and the code hash, expiry and attempts (`destinationRecord`); or a chat with its encrypted secret) and connections (a rule: name, destination, all projects or their ids, levels, active; reading one fills the destination fields). A connection needs a confirmed destination; deleting a connection keeps an email destination, so a confirmed address stays confirmed, and deletes a chat's with its secret; a connection left without projects by a project's deletion is turned off. The outbox channel of a message is its connection's id.
  - `first_seen`/`last_seen` use the server receive time, not the SDK clock; the times of events and logs are the SDK's, moved by the device's clock drift when the envelope's `sent_at` is a minute or more from the receive time (`ingest.clockDrift`, applied in `parseItems` (`items.go`, called by the pipeline's processors) by `sdkTime`, which replaces a time more than 30 days before or a minute after the receive time, as Sentry's Relay does: milliseconds sent as seconds would otherwise reach years JSON cannot encode; the event page says how far the clock was off, `services.ClockDrift`). `Write` reports `NewIssue`/`Regression` per event (`store.SaveResult`) (a resolved issue that happened again goes back to unresolved; ignored stays ignored) for notifications.
  - Issues are kept in memory as well (`issueTable`), so issue lists filter and sort there (`issueOrder`, ties by id); `IssueFilter` date ranges apply to `DateField`: any event in range or first/last seen in range (default; the cleanup may have deleted the events), `first_seen` or `last_seen` (only the API exposes the choice, `date_by`). Issues sort by last seen, first seen, events or project; random ids have no order to sort by.
  - Logs and events are read newest first through their indexes; time marks (`marks.go`) turn date ranges into sequence ranges. Text search of logs compares each line (`textutil.ContainsFold`), first on the stored bytes when the text has no character JSON escapes (`rawSearchable`), so most lines are never decoded; a count that the index walks answer exactly counts keys (`countByKeys`); log counts (the pager) stop at `store.LogCountLimit` (10000; `CountLogs` returns `more`, the pager shows "of 10000+").
  - API lists fetch `limit+1` rows; `store.Page` trims them and says whether a next page exists (cursor pagination). The web app's lists use pages (`Offset`/`Limit` of `IssueFilter`/`LogFilter`, the API's offset cursor); issues are filtered in memory (`filterIssues`, shared by `ListIssues` and `CountIssues`), logs by walking an index newest first.
  - `store` never imports `sentry`: callers map to `NewEvent`/`NewLog`.
- `internal/server`: `net/http` ServeMux with method patterns (`"GET /health"`), wrapped in a request-logging middleware. Built from `server.Options`; depends on small interfaces (`Pinger`, `http.Handler` for ingest, `Routes` for the API and the web app), so tests use fakes. Mounts ingest (open), `/health` (open; 503 when `Store.Ping`, a read of the store, fails), the API wrapped in `protectAPI` (IP allowlist first, then API token); MCP, OAuth, the web app (`Web`, every address no other route takes) and its API (`UIAPI`, a `UIRoutes`: routes plus the handler of every other address under `UIAPIPrefix`) use the IP allowlist plus their own authentication. `RESTPrefix` (`/api/v1/`) and `UIAPIPrefix` (`/api/ui/`) are defined here; the one `"/api/"` fallback (`unknownAPI`) sends `/api/ui/...` to the web app's API (a login, then a JSON 404) and anything else to a JSON 404 behind the token. `headers.go`: `ContentSecurityPolicy` (the one builder: script sources such as the page's inline hashes), `SecurityHeaders` (policy, nosniff, `Referrer-Policy: same-origin` (no-referrer would make browsers send `Origin: null` on same-origin POSTs), `X-Frame-Options`), `SameOrigin` (Origin's host is the request's, and https when the request is (`IsHTTPS` with the trusted proxies); oauth compares with PUBLIC_URL on purpose), used by `web` and `api/ui.go`.
- `internal/server` (`access.go`): `ClientIP` (uses `X-Forwarded-For` only when the direct peer is in `TRUSTED_PROXIES`, read right to left; entries may carry a port; addresses are compared unmapped and without an IPv6 zone, `comparable`, and IPv4-mapped networks in the settings are stored as IPv4), `FromTrustedProxy`, `RequireAllowedIP` (403, a debug log line with the address seen), `RequireToken` (constant-time; empty `API_TOKEN` closes the REST API).
- `internal/server` (`json.go`): `WriteJSON`/`JSONError` for JSON responses (`{"error": ...}`). Ingest keeps its own `writeError` because Sentry SDKs expect `{"detail": ...}` plus `X-Sentry-Error`.
- `internal/api` (the catalog): the one catalog of requests, served as the REST API, as MCP tools (like AdminForth's endpoints → tools) and to the web app. `Endpoints(projects, services.All)` lists them in order; handlers reach data only through `services.All` (no store), so tools and pages apply the same rules (with nil arguments it only serves to read the definitions); each is `Define(Endpoint{Name, Description, ReadOnly, Idempotent, Destructive, Confirm, Admin, Transports, OpenWithTemporaryPassword}, handler)` with `handler(ctx, Call, In) (Out, error)`: the input schema comes from `In` (`json` + `jsonschema` tags, `jsonschema.For`) with the enums of `Choices` and the bounds of every `limit` (`DefaultLimit`, `MaxLimit`), `Run` validates the input map against it and decodes it. A new tool or API route = one entry + its handler; nothing else to register. `Call` has the `Transport` (`TransportREST`, `TransportMCP`, `TransportUI`; a `Call` without one runs nothing), the `Viewer` (the user of the agent or the web app; empty for the REST token), the `Actor` (recorded in the history) and the server `Address` (DSNs); `ForAgent()` is true unless the transport is REST or the web app (fail closed), and then `call.Text` redacts free text with `agentprompt.Redact`. Output is JSON, or `api.Text` written as is (the agent prompt of `get_issue`/`get_event`). Errors: `Invalid(...)` (400 / tool error as is), `ErrNotFound`/`store.ErrNotFound` (404), anything else logged by the transport and reported as "internal error" (`Outcome`). A refused form is `problemsError` (the problem of each field, renamed to the input's names) or `duplicateError` (the connection that already sends there): over HTTP the body is `ErrorBody` `{error, fields?, duplicate?}`, so a page shows each problem at its field, MCP gets the joined message (`TestInputErrorBody`). Lists: `Page{items, next_cursor}`, 20 rows by default, at most 100, plain-number cursors (offset for issues/projects/deliveries, at most `store.MaxOffset` (`parseOffset`; `ListIssues` clamps too, since offset+limit must not overflow), last id for events/logs; `list_users` and `list_connections` return every row in one page). Every endpoint names its `Transports` (`Define` panics without; `AllTransports`, `ActsAsUser` = MCP and the web app, or one): `Run` refuses (as `ErrNotFound`) what `AllowedFor(call)` denies: an endpoint its transport does not serve, for a user without `CanAdminister` an `Admin` one, and in the web app, while the user has a temporary password, anything without `OpenWithTemporaryPassword`; the token runs every REST endpoint. REST only: `get_event_payload` (raw payload), `list_trace` (log attributes), their output must not reach a model provider (the web app reads the payload, indented, inside `get_issue_details`). `ActsAsUser` (`manage.go`, `notifications.go`): account, agents, projects, users, notification connections and email confirmation, acting as the user (`Users` and `Agents` check the user's role and return `ErrForbidden`, reported as not found; `Projects`, `Connections`, `Verification` and `Deliveries` check no role, so their endpoints need `Admin`); form rules are shared because tools pass the form's fields as `url.Values` to `services.Projects.Save`/`Connections.Save`, starting from `FormValues` of the stored record so fields not given keep their values. `get_storage` (`session.go`, the web app only): the database size against `MAX_DATABASE_SIZE` (`services.Projects.Storage`) with each project's part (its bytes before compression, in proportion), other, `last_received` and `counting`, for the Projects page. `get_session` (`session.go`, the web app only, `OpenWithTemporaryPassword`): the viewer (`user`, with `display_name`), `can_administer`, `app_name` (`services.All.AppName`), the unresolved count and `project_colors` (the shown color of every project by name, `services.Projects.ColorsByName`; badges set it with the `style:` directive), for the app's menu and badges. The web app's own endpoints (never MCP, mostly because their output is unredacted): `count_issues`, `list_issue_levels` (the count and level choices of the issue list, from the filters `list_issues` takes, `issueFiltersInput`; `issueOutput.mcp_reference`, `agentprompt.MCPReference`, is filled only for the web app); `get_issue_details` (`issue_details.go`: an issue with its history, its 20 newest events (`next_cursor` for `list_issue_events`, whose items carry `received_at`) and one event (`?event=`, the latest by default) read by `services.Issues.Details`: `event_state` shown, unreadable, missing (not stored, or another issue's) or none (`services.EventState`, generated as a union through `outputSchemas`), the facts, exceptions outermost first with frames newest first, maps as name-sorted pairs, JSON indented by Go, related logs, the stored payload and the agent prompt); `apply_issue_action` (resolve, ignore, reopen or delete 1 to `services.MaxActionIssues` issues, `services.IssueActions` as choices; invalid ids 400; deleted ones skipped; delete needs `CanAdminister`, checked by `services.Issues.ApplyAction`, else 404); `list_cleanups`, `get_project_setup` (every role), `get_project_defaults` (admin); `get_user` (admin, `{user, can_manage}`); `get_mcp_setup` (`agents.go`: how to connect an agent); `get_connection` (saved tokens masked by `textutil.MaskSecret`, never whole), `get_connection_defaults`, `test_chat`, `count_deliveries` (all `Admin`). `set_connection_active` (also MCP) changes only `active`: a whole-form save would refuse a connection whose tokens cannot be read. `list_users` rows are `{user, can_manage}`; `userOutput` has `display_name` and `created_at`; `list_agents` returns `user_id`, `owners` (whose agents the caller may list, only when more than one) and `connected` per agent; `get_project` gives `shown_color`, and an unknown project is `ErrNotFound` with a message naming it for agents. `create_user`/`update_user` take the roles of `store.AssignableRoles` as `Choices`. `list_projects` gives every role `from_env` and the recorded log levels as an explicit list, highest first (`config.Recording.RecordedLogLevels`, the one rule, also behind `services.Projects.FormValues`). `typescript_test.go` (`TestTypeScriptCatalog`) generates `web/src/lib/api/catalog.gen.ts` from the endpoints the web app may call: inputs from `InputSchema`, outputs from the handler's output type (`Define` keeps it; - `internal/sentry`: the SDK wire format only (envelope splitting, `Event`, `Log`), no HTTP or storage. Decoding is deliberately lenient: custom types (`Timestamp`, `Message`, `Tags`, `ExceptionList`, …) accept every shape the protocol allows and fall back to the zero value on an unexpected one, because losing a field is better than losing the error report; every other field goes through `Decode` (`decode.go`, also used for the request, contexts and breadcrumb data by the issue page (`services.Issues.Details`) and the agent prompt): a plain decode first (`ExceptionList`/`BreadcrumbList` strict in it), and only when it fails one walk over a `jsontext` token stream (one more pass however deep the field, `TestWrongTypedFieldCostsLittleMore`), where numbers and booleans fill string fields as their text and objects or arrays leave them empty (like Relay's `LenientString`; `release: 5`, `lineno: "12"`), booleans count only as JSON booleans (as ingest's `isAppFrame` reads `in_app`), and list elements or map values of the wrong shape are dropped one by one, so an odd frame keeps the rest of the exception chain. Only a payload that is not a JSON object (`null` included) fails `ParseEvent`/`ParseLogs`. `Event.Raw` keeps the full payload; `Event.Trace()` gives trace and span IDs; `NormalizeEventID` turns UUID form into 32 hex.
- `internal/ingest/grouping`: decides which events are one issue. Custom SDK `fingerprint` wins (`{{ default }}` expands to the default). Default: exception chain types + in-app frames as file/module + function + source line (`context_line`), no line numbers; events with the same fingerprint in one project are one issue, every exception of the chain adds its type and its frames (the in-app ones when there are any, otherwise all frames after the async boundary); line numbers are left out so a deploy that shifts code opens no new issue, and the source line keeps two throws in one function, or two functions with the same name, apart; in-app is `sentry.Frame.IsInApp`: marked by the SDK and not under `node_modules/` (a browser SDK marks every frame of the page's origin in-app, and Vite serves libraries from there as `/node_modules/.vite/deps/`), and only frames after the newest async boundary count (a function with `*`, as Firefox and Safari mark it, e.g. `promise callback*queueFlush`), so the path that scheduled the callback does not split one error into several issues (JS names `handler: () => {}` after the property, so the function name alone merges unrelated errors); anonymous functions without source use the line number; file and module paths drop origins, query strings (`tsx watch` adds `?<timestamp>`) and bundle hashes (8+ hex characters after `.`, `-` or `_`: webpack, Next.js, Turbopack; 8 base64url characters after `-` or `.` that only extensions follow, the one nearest the end: Rollup 4/Vite 5+, SvelteKit, Astro; only with a digit or an uppercase letter after the first character, so `use-settings.js` and `user.reducers.js` stay and an all-lowercase hash, about 1 in 400, opens a new issue); if no frame has source code (browser), the normalized error text is added. An exception without frames adds its normalized value instead; messages (and `captureMessage`'s exception without a type) group by their normalized text, so "order 890" and "order 891" match. These rules and `docs/sdk.md` (Grouping) are the one description of grouping; change grouping only with tests, because a change regroups new events into new issues.
- `internal/platform/secret`: AES-256-GCM `Box` keyed by `SECRET_KEY` (SHA-256 of the string); encrypts chat tokens and webhook URLs stored in the database. Without `SECRET_KEY`, main uses `secret.KeyFile(DATA_DIR)`: `secret.key` generated at the first start (0600, written whole via a temp file and a link, a damaged one stops startup instead of being replaced).
- `internal/notify`: alerts about new and regressed issues (the ingest write reports them; `StoreSink` calls `Notify` with the project id). Destinations are **connections** stored in the database and managed on the web app's Notifications pages: type (email/telegram/slack), address or encrypted secret, projects (or all, including future ones), levels, active. Delivery goes through the outbox (collection `outbox`), so it survives restarts and outages:
  - `Notify` only queues in memory and never blocks ingest; it cuts the title and culprit to what an issue keeps (`store.MaxTitleLength`, `MaxCulpritLength`) and environment and release too. A dispatcher goroutine reads the connections (once per burst: again whenever its queue has emptied), sends each notification to those that match (one outbox batch for all of them) (`matches`: active, verified, project, level; unknown levels count as errors), applies the flood limit per connection (5 per minute individually, the rest as one `Summary` when the window ends; a window keeps only the count and the first `maxSummaryItems` held notifications, so a flood of large events does not pile up in memory) and writes outbox rows.
  - One worker goroutine per connection (started on demand, and at startup for connections with pending messages) sends due messages oldest first, so a destination stuck in retries (an SMTP provider rate-limiting; the free Mailtrap sandbox takes about one email per few seconds) does not delay the others. A failed send ends its pass and waits for its retry, so later messages overtake it (one message the channel refuses does not hold back the rest for `NOTIFY_RETRY_FOR`); a `RetryAfterError` pauses the worker for its delay; a message sent while the store refused to record it is not sent again (`worker.unmarked`, recorded on the next pass). The channel is rebuilt from the stored connection for every batch of due messages, so edits apply to queued messages; a disabled or deleted connection fails them (`errGone`). Retries follow `Schedule` (2s, 10s, 30s, 1m, 5m, 15m, 30m, then hourly) until `NOTIFY_RETRY_FOR`; `RetryAfterError` carries a channel's own rate-limit delay. Saving an active connection makes its waiting messages due at once (`store.RetryOutboxNow`, called from `services.Connections`), since a save is usually the fix; `services.Connections.RetryNow` does the same without a save; the worker picks them up on its next poll (`PollInterval`, 1s). Every failed attempt is logged as a warning, giving up as an error.
  - `CleanOutbox`, the job of the notifications lane (`jobs.go`), deletes sent messages after `NOTIFY_KEEP_SENT` and failed ones after `NOTIFY_KEEP_FAILED`.
  - `Close` on shutdown writes the in-memory queue and pending summaries to the outbox and sends what is due; messages waiting for a retry are sent after the next start. Only a killed process loses the in-memory part, apart from what `Notify` drops with a warning while the queue (`QueueSize`, 1000) is full.
  - `Factory` builds channels from connections (decrypting secrets with the `Box`), sends test messages (`SendTest`) and is shared with services. Channels implement `Send`/`SendSummary`: `Slack` (incoming webhook, `{"text"}`, also Mattermost/Rocket.Chat, so text outside code goes through `slackText`, which also breaks `@all` mentions and Markdown images; or a bot: `SlackSecret.BotToken` + `Channel` posts through `chat.postMessage` and puts the agent prompt as a code block in a thread under each error (cut to a Slack message by `agentprompt.BuildWithin`, which shortens only the error data, so the end marker and the reminder stay), since a webhook does not return the message timestamp; a failed thread post is dropped so the message is not sent twice), `Telegram` (bot API, HTML parse mode; errors must not include the URL, it holds the token; an error is one message: the agent prompt as a `.md` file via `sendDocument` with the alert as its HTML caption (max 1024 characters, so details are capped), since a message holds 4096 characters and a `copy_text` button 256; a refused file falls back to a plain message, a rate limit is retried as usual; test messages and summaries stay `sendMessage`) and `Email` (plain SMTP via net/smtp, no provider SDK: STARTTLS, or TLS on port 465; multipart text + HTML from `templates/email.html`, styles inline for mail clients; `SendVerificationCode` for new addresses). A message carries the event's id (`Notification.EventID`), not the event: each attempt reads the stored one (`notifier.storedEvent`; deleted meanwhile, it goes out without details), so the outbox, which the size limit does not count, never holds copies of events. Email shows at most 10 exceptions, 15 frames with 5 source lines around the throwing one and 30 tags, every text cut (`fieldLength`; values and messages 2000 characters); every prompt (`Build`: `get_issue`, the issue page, Telegram and email) is cut to `agentprompt.MaxLength` (100000 characters) in its error data, the Slack thread to a Slack message (`maxSlackText`). Short formats share `format.go`; stack reading uses `sentry` methods (`OutermostFirst`, `NewestFirst`, `IsInApp`, `SourceLines`) like the issue page does. `Factory.TelegramURL` points to a fake Telegram API in tests, so no test reaches api.telegram.org. Tests use fake HTTP and SMTP servers (`fixtures.FakeSMTP`) and a real database; assertions do not depend on timing (`waitFor`).
- `internal/agentprompt`: `Build` (instructions + `Describe`) writes a prompt that asks a coding agent to reproduce and explain an error with evidence, without changing code or calling tools that change the monitor (the developer checks it and asks for the fix); the error data comes from anyone who can send errors and a copied prompt reaches the agent as the developer's own message, so it sits between `=== BEGIN/END ERROR DATA <label> ===` lines (`markers`: the label is a hash of the data, so the data cannot contain its own end, homoglyphs included; look-alike markers inside it are replaced too, `fakeMarker`) and a reminder not to follow anything in it comes last, shared by the issue page (its "Prompt" button, from `get_issue_details`), email, Telegram and the Slack bot (`BuildWithin` cuts it to a length in the data only; one input, `notify.promptInput`: `agentPrompt` for Telegram and email, `slackPrompt` for the Slack bot) (attached as `<project>-<level>-<issue id>.md`, e.g. `backend-error-k3x9q2mf.md`: mail clients run no script, so it cannot be copied by a button there). It is bounded: at most 10 exceptions (outermost first), 40 frames each with 7 source lines around the current one, 30 tags, 30 breadcrumbs, 50 logs, and `agentprompt.MaxLength` (100000 characters) in all. It leaves the server, so it is built from an allowlist (the project, kind (new issue or regression), issue title, level and location (culprit); the event's platform, release, environment, transaction, time and SDK name and version; runtime/os/browser names and versions; exception chain with the mechanism type and handled; every frame's function and file:line:col, with source for in-app code, for every frame when none is in-app; message; request method + path; breadcrumbs, HTTP ones as method, path and status; non-sensitive tags; related log lines with time, level and body; the issue's status, event count and first/last seen), never from the raw event; left out on purpose: user data, request headers, cookies, bodies and query strings, server names, frame variables, `extra`, SDK contexts other than runtime/os/browser, log attributes and panel URLs; kept free text, tag names, platform, SDK name and version and a frame's file or module included, goes through `Redact` (IPs, URL hosts, emails, credentials, JWTs, home directories → placeholders; anywhere Telegram bot tokens and Slack webhook paths, `redactServiceTokens`, since HTTP clients print paths without a scheme; in URL paths also runs of 16+ letters mixed with digits, `redactURLPath`). SDK trace IDs are unchecked, so agents get them only as 32 hex (`TraceID`, `Call.TraceID` in the catalog; `get_issue` prints its trace line above the prompt). `prompt_test.go` lists what must never leak; extend it when adding a field.
- Cleanup by size (`internal/storage/database/cleanup.go`): when the database reaches `MAX_DATABASE_SIZE` it deletes the least useful data down to 80%, in the order of `docs/configuration.md` (Retention), which is the one description of it; the code's step list is the other. Checked by the size check of the database lane (`CheckSize`) at startup, every 10 minutes and after every 50 MB written (`CleanupWake`), with a 5-minute limit per pass (a stopped run goes on at once, from where it stopped); the inbox compaction of the same lane (`CompactInbox`) runs at start and halfway between the checks, limit or not, but only when no envelope came for `quietFor` (2 s): processed envelopes, credentials included, keep their bytes in the files until a compaction reaches them, and under writes goleveldb repeats a range compaction for as long as new files come (measured: 60 s during a peak, holding the lane); `TestCompactInboxWhenQuiet`. Each check runs `ReduceAging` (events turning a month old are thinned in the background, only while the limit is on; it deletes nothing); when ingest is quiet it first compacts the inbox and the issues (where deleted and rewritten records pile up) and deletes only if that is not enough; decisions come from the byte counters. A run is a record in the `cleanup` collection (status, goal, step, position, counts per step and project; the last 100 kept, `store.CleanupRunsKept`) saved in the same batch as each delete, so a restart goes on where it stopped (unless `MAX_DATABASE_SIZE` changed: the run then ends as failed, `limitChanged`, and a new one starts from the new limit); every batch reads the issues as they are under the write lock and stops at 2000 records or once enough is freed; one issue's events spread over batches go on after the last event deleted (`deleteIssueEvents`), so no walk passes deleted keys again. The key ranges it deleted from are compacted afterwards. `Store.Verify` checks indexes, counters and issue counts (tests run it; `TestBurstWithCleanup` runs a burst through the pipeline during cleanups).
- `internal/storage/projects`: `Registry` keeps the projects (collection `project`): `Open` seeds `PROJECTS` at every start (`store.SeedProject`: created with its name if missing, otherwise only its key set to the env value, the name and settings from the web app kept; a name or key taken by another id stops startup), then caches the list in memory (`List`, reloaded after every change), so ingest checks a project without a database query per envelope. Projects from env (`FromEnv`) can be renamed and edited in the web app (`Registry.Update` keeps the env key) but not deleted; projects added in the web app get a random 8-digit id and a generated 32-hex key, are fully editable, and `Delete` (not bound to the request's ctx) removes the project and its connection entries in one batch (`store.DeleteProject`, which also writes a `project_purge` marker and adds the id to `goneProjects`, so `Write` drops any later event or log of it), reloads the list, then deletes its issues, events and logs (`PurgeProjects`; the `project purge` job of the database lane goes on with one stopped by a restart). Project ids are 32-bit in keys, so `PROJECTS` ids stop at `config.MaxProjectID` and `GetProject` answers not found above it. Each project has a color (`''` follows `config.ProjectPalette`, named colors generated into `catalog.gen.ts` as `projectPalette`, by id; a new project stores the color its form showed, since its random id's palette color is not known yet, and on an existing one choosing its palette color stores `''`; `config.ValidColor` accepts only `#rrggbb`); the web app gets every project's shown color from `get_session` (`project_colors`) and sets it with the `style:` directive, since the CSP forbids inline styles; emails get `Notification.ProjectColor`, which `projectColor` validates for the inline style. Project and level filters take several values (`ProjectIDs`/`Levels` in `IssueFilter` and `LogFilter`). Issues, events and logs also count their bytes per project (`projectCounter`, group counters); events have a `project` index (project, level, seq) like the logs; both came with the backfill `project-sizes`, run by the `project sizes` job of the database lane (`Store.Backfill`: at start, then every `CleanupInterval` from `config.BackfillAt`, `BackfillTimeout` per pass) until done. `Store.ProjectUsage`: bytes per project, `Counting` while the backfill runs, and last received (the newest issue's last seen or the project's newest log). `Store.Verify` also checks the group counters.
- `internal/ingest` (`compact.go`): `compactEvent` drops what does not help a fix before an event is stored: source and vars of library frames (not `IsInApp`, so `node_modules` too) when the stack has in-app frames (grouping then uses only in-app frames, so it is unaffected), `modules`, `debug_meta`, `sdk.integrations`/`packages`, breadcrumbs beyond the newest 50. An event is kept for weeks, many per issue, so its size is paid many times over; `debug_meta` goes because the server does no symbolication; the SDK's name and version stay, everything else is kept as sent.
- `internal/ingest` (`scrub.go`): removes credentials from SDK payloads before they are parsed or stored (ingest calls it), so the web app, the API, notifications and stored records never hold the session cookies or tokens of the monitored app's users; only the inbox holds the envelope as it came until it is processed (and a backup taken meanwhile; its bytes stay in the files until a compaction, see the cleanup). Key-name based (`isSensitiveKey`: password, token, auth, cookie, session, api key, …; `[name, value]` pairs too; log attributes keep their `{value, type}` shape) plus, in strings (`scrubText`), Bearer/Basic credentials (a token, not a word: `isToken`), the userinfo password of URLs (the username stays) and sensitive parameters of queries and fragments (OAuth implicit flows put `#access_token=` there) of absolute URLs, relative ones (`GET /reset?token=… 200`) and bare query strings (no `/:?#` before the first `=`), each URL found inside text too, nested ones in a query (`?next=/reset?token=…`, `?redirect=https://user:pw@…`) and every `scheme://` of a run included; a password may hold `/`, `?`, `#` or `@`, a numeric port is not one; only the values change, the rest stays byte for byte. A removed value becomes `[Filtered]` (`filteredText`), the whole value under a secret's key (an object with a `value` member becomes `{"type":"string","value":"[Filtered]"}`, nothing else kept); a string that is one JSON object or array (a request body sent as text) is scrubbed by the payload's rules (`scrubJSONText`, one level only: its own strings are free text, so the cost stays linear, `TestNestedDocumentsInTextStayLinear`), and in other text (`scrubFreeText`) the string or number values of `"key": value` pairs whose key names a secret are replaced, a value cut at the end of the text included (`scrubQuotedPairs`, one byte pass); SDKs with `sendDefaultPii` send request cookies and the `Authorization` header, so the key rules apply to every part of a payload (headers, cookies, frame variables, breadcrumb data, extra, contexts, log attributes). It is one pass over the JSON tokens (`encoding/json/jsontext`, `scrubValue`/`scrubObject`/`scrubValues`), no tree; only an array led by a secret's name is read as a tree, so deep nesting stays linear (`TestDeepNestingStaysLinear`). Data stored before it existed is not rewritten.
- Levels to record: events (errors and messages) of every level are stored (issues group them, notification connections filter by level, SDKs filter noise themselves); only logs are filtered: each project may set its own log levels (`Project.LogLevels`; nil = the `RECORD_LOG_LEVELS` default, an empty list = none, kept apart through JSON by `keepNone`; the form stores the default as NULL so a project follows it). `StoreSink` stores levels under their canonical names (`config.EventLevel`: critical = fatal, warn = warning, log = info, trace = debug, unknown = error; `config.LogLevel` for logs), so filters, notifications and badges never translate them again, and drops logs of levels not recorded before storing.
- `internal/ingest`: `POST /api/{projectID}/envelope/`. Order matters: CORS → public key (query `sentry_key`, `X-Sentry-Auth`/`Authorization`, or the envelope header `dsn` when sent via a tunnel: only the first line is decompressed for it (a br body, which can only be read whole, is refused there with 401: only sentry-python sends br, always with the key in the request), `requestBody.header`, at most `MaxHeaderBytes`, its buffer growing as bytes arrive; with the key in the request nothing of the body is read before project auth) → project auth → read/decompress body (gzip, deflate, br (sentry-python); 20 MB cap before and after decompression; all bodies being read share `MaxReadingBytes`, 80 MB, one project at most half of it (`readBudget`, counted as the buffers grow, a br body is read whole first, then the window its stream declares (up to 16 MB, which the decoder may fill before any output) is held while it is decoded in memory, so a stalled client holds only the bytes it sent; 429 with `Retry-After` beyond it), and a body must arrive within `BodyReadTimeout`, 10 s) → parse the envelope; one without `event` or `log` items gets 200 at once, neither counted nor stored (`storesItems`: a 429 stops every category in the SDK, so span envelopes must not use up the limit of errors) → per-project rate limit → the inbox (`Pipeline.accept`: the envelope as it came, with the project and the receive time; 429 above `config.MaxInboxBytes`, 20% of `MAX_DATABASE_SIZE` (of its default when the limit is off), so a backlog can never crowd out stored data) and the answer. The queues to the processors carry an entry's sequence, project and size only (`Pending` reads no bodies); a processor reads the body (`InboxBody`, a slice of the engine's copy, `kv.Collection.GetValue`, so one copy, `TestInboxBodyCopiedOnce`) once its bytes fit `ParseBytes` (32 MB for the envelopes being parsed or waiting for the writer, freed when stored), and an entry already stored gives nothing, so one handed both from the fresh queue and by a scan of the inbox is stored once (`TestScanDoesNotStoreTwice`). A processor then runs `scrubJSON` on every log item and, for events, `prepareEvent` (`compactEvent` over the token decoder and encoder of `scrub.go`, one pass; `prepare_test.go` checks, also as a fuzz target, that it gives what the tree pass it replaced gave) → parse all items → the writer's batch, which also deletes the inbox entry (a batch failing on a record JSON cannot encode is written one envelope at a time and that envelope is dropped, `storeBatch`, since no retry would fix it). All items are parsed before anything is stored, so a malformed item (not JSON, or not an object) drops the whole envelope. Only `event` and `log` items are stored; other types are dropped. `NewPipeline` builds the handler with its pipeline, so every envelope, the tests' too, goes through the inbox. `StoreSink` computes the grouping fingerprint, maps Sentry types to `store.NewEvent`/`store.NewLog` and reports what the writer stored (log lines, notifications). Rejections are logged at debug level (ingest is public, so warn-level logging would be a flood vector).

### Projects and DSNs

`PROJECTS=1:backend:<key>,2:frontend:<key>` — `id:name:public_key`, seeded into the database at every start (more projects can be added in the web app, see `internal/storage/projects`). IDs are chosen by the user and must stay stable: the id is part of the DSN (`http://<key>@host:8000/<id>`) and is stored with every event, so it must never be derived from list order. Each service (backend, SSR, frontend…) gets its own project; all live in one container and the web app shows which project an error came from. The Projects page shows each DSN: at `PUBLIC_URL` when set (path prefix kept), else at the address the web app was opened with (https behind a trusted proxy that sends `X-Forwarded-Proto`). The scheme is part of the DSN; SDKs cannot parse one without it.

Auth model: users with roles (the superadmin from env at the first start, the others added in the web app) and an API token, plus an IP allowlist for the web app, MCP and the API; the ingest endpoint stays open (protected only by DSN keys, CORS `ALLOWED_ORIGINS` and rate limiting) because browsers send errors directly.

## Conventions

- Tests sit next to the code (`*_test.go`, same package unless they drive the whole server); fixtures go in `testdata/`. When adding a check, make sure the test fails without the fix.
- Blank lines (enforced by `wsl` in `.golangci.yml`, same rule as the team's TypeScript projects): always a blank line before `if`/`for`/`switch`/`defer`/`return`, including `if err != nil` right after the call; consecutive assignments stay together. Run `make fix` after editing; `--fix` only adds blank lines, it never removes extra ones.
- Everything in the repo is in English: code, comments, test data, interface text. Test values are plain and conventional (`root` / `root-password`, `admin`), not invented strings in other languages.
- Use descriptive variable names (`settings`, `database`, `batch`, `connectionList`), not one-letter ones. Keep the standard Go idioms `err`, `ctx`, `t`, and `w`/`r` in HTTP handlers.
